A profile of A2UI 1.0

S2UI — Supervisor-to-UI

Public draft · release 0.1.3 · protocol line S2UI/1

S2UI standardises how a supervisor — a system that runs a team of agents on a task, in stages, in work units, under a verdict, sometimes waiting on a human — publishes the state of its runs so that a user interface can render them, and how that interface asks the supervisor to act.

Its core object is a snapshot digest of a run — state, stage, work units, verdict and outstanding human attention — which a UI can render correctly after reconnecting, restarting, or arriving late, with no event replay. Surfaces are composed from digests deterministically, by code and templates — never by an LLM in the observability path.

The specification

S2UI-1.md — the four parts, the MCP embedding, versioning and conformance, in RFC 2119 language. Raw Markdown.

Source repository

The public repo: spec, schemas, examples, validator and installation guides. MIT.

Install S2UI

Three consumer paths: MCP host / LLM agent, supervisor implementer, UI host.

Honest position: today there is exactly one producer (a private reference supervisor) and no built consumer. The protocol line stays at 0.1.x until a second, independent implementation exists.

Examples

  • dogfood-persistence.rundigest.json — a real run: a supervisor fixing its own persistence bugs. Paired real surface (composer output).
  • parallel-packages.rundigest.json — a real run with parallel work units. Paired real surface (composer output).
  • beth.catalog.json — draft catalogue example; its instructions field is the LLM installation mechanism.
  • answer-attention.command.json — draft command example.

Validate them all with node tools/validate from the repository — no dependencies.

Differentiation

Against raw event streams (AG-UI-style): a stream tells a UI what just happened in a live session; S2UI's digest is a snapshot a UI can render from after arriving late. Against product-specific supervisor contracts: S2UI is a standalone, implementation-independent profile with a published schema — a supervisor keeps its own lifecycle, roles and runtime; S2UI only constrains what it publishes and the commands it accepts.
